> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A no-auth `status` connector: up to 8 services (curated statuspage.io picks + custom URLs), rendered as a quiet dot row in the bottom band that only grows text when something is actually wrong.

**Architecture:** RSS's shape exactly — auth `'none'`, `secretFields: []`, per-service origins granted on add and released share-aware on remove. `fetchStatus` fans out per service in parallel; a failed service shows a gray `unknown` dot (staleness is actively misleading for a STATUS product, so failures do NOT carry a previous green — the one deliberate departure from the house prev-carry idiom, documented in code). The widget joins `<aside data-zone="bottom">` above the crypto strip; its worst-case height is bounded by construction (dot row + max 3 trouble lines) and the band's floors are re-derived by measurement.

**Tech Stack:** unchanged. No new deps. No schema bump (`CONNECTOR_IDS` growth is additive; configs are sparse per-key; layout keys are sparse).

**Spec:** `docs/superpowers/specs/2026-08-10-wave3-design.md` (W3-SP2 section — binding, with two pinned deviations recorded there-vs-here: (1) stored service entries are uniform `{ name, url }` — the spec's `key?: CuratedKey` adds nothing at runtime since curated picks are just prefill; (2) the spec's curated list is a CANDIDATE list — Task 83 verifies each endpoint live and ships only statuspage-v2-conforming ones).

## Global Constraints

- Quiet day stays quiet: all-green renders the dot row ONLY. Trouble lines appear per affected service, worst first, capped at `MAX_TROUBLE_LINES = 3` (the cap bounds the band's height math — construction-time, not a runtime clamp).
- Copy exact: card label `Status`, blurb `Green dots for the services you depend on`; settings copy pinned in Task 85; trouble line format `{name} — {description}` (statuspage's own description text, e.g. "Partial System Outage").
- Dot colors: `none` → `bg-emerald-400`, `minor` → `bg-amber-400`, `major`/`critical` → `bg-red-400`, `unknown` → `bg-fg-muted/40` (gray). Each dot carries `title="{name}: {description or 'unreachable'}"`.
- Indicator taxonomy is statuspage v2's: `none | minor | major | critical`; anything else (parse failure, network, non-OK, unrecognized value) → `unknown`.
- Per-service isolation: one service failing never blanks another; the fetch never rejects.
- Gesture chain in settings: `ensureOrigin` first await, zero awaits ahead; https-only validation via `originPattern`; duplicate detection on the resolved URL; share-aware revoke on remove (write-result survivors + `releasableOrigins`).
- House laws: zero-hooks-in-the-gate; no-husk (no services → null); never data-gate what CSS tier-gates; fixture law (sweep at true display max: 8 services, 3 trouble lines); monotonic visibility.
- Verification per task: `npx tsc --noEmit` + `npx vitest run` + `npm run build` ALL PASS 0 FAIL; harness tasks add `npm run build:preview` + FULL FOREGROUND `node scripts/preview.mjs` (backgrounding it has killed agents).

Empty list → `{ services: [] }`, no fetch.
